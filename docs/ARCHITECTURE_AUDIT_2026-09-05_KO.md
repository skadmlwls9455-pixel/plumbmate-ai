# 구조·기획 일치 감사 및 통합 인계

> 이 문서는 9월 5일의 감사 기록이다. 이후 수정 상태는 `FOUNDATION_INTEGRATION_2026-09-05_KO.md`와 `UX_CONTEXT_REVIEW_2026-09-06_KO.md`를 따른다. 아래의 "남은 결함"은 당시 기준이며 최신 코드에 그대로 남아 있다는 뜻이 아니다.

## 범위와 판정

검토 대상은 `main@81da97c`, 그 위의 루멘 로컬 변경(195개 테스트), [페이블 PR #1](https://github.com/skadmlwls9455-pixel/plumbmate-ai/pull/1)의 `d45a4d0`이다. 테스트 수가 같다고 같은 테스트/코드라는 뜻은 아니다. PR은 검토 당시 draft/open이었으며, [CI run 4](https://github.com/skadmlwls9455-pixel/plumbmate-ai/actions/runs/33967059060)의 macOS·Ubuntu 작업 성공을 API로 확인했다.

**결론: 통째로 다시 만들 필요는 없다. 게임/외부 앱/전송/공급자/세이브 판별의 큰 경계는 나뉘어 있다. 하지만 경계마다 적용하는 규칙이 다르고, 명령 처리와 소켓 파일에 서로 다른 책임이 쌓이는 중이다. 새 RP 기능보다 통합 계약과 실제 게임 왕복 검증이 먼저다.**

이번 최신 요청에 따라 배포·릴리스·즉시 병합을 보류한다. 게임은 메인 메뉴에서 정상 종료했지만, 수정본을 실제 Mods에 설치하거나 가족을 불러오거나 저장하지 않았다. 이 문서는 인게임 통과 보고서가 아니다.

## 1. 모듈화 상태

행 수는 리팩터링 근거를 찾기 위한 보조값이며 줄 수 자체를 품질 점수로 쓰지 않는다. 아래 수치는 이번 로컬 스냅샷 기준이다.

| 경계 | 현재 상태 | 판단과 필요한 정리 |
|---|---|---|
| 게임 ↔ 외부 앱 | 소스 루트와 Python 런타임 분리. 게임은 EA 조회·비차단 소켓, 외부 앱은 모델·서버 작업자 담당 | 유지. 게임에서 3.11 companion 모듈을 import하는 공용화는 금지 |
| `commands.py` 443행 | 치트 등록, 스냅샷, 파일 요청/응답, 설정 경로, 자동 연결 수명주기, 전역 상태 | 책임 과밀. `game_adapter`(EA), `turn_bridge`(요청 상관관계), `bridge_runtime`(설정/연결)을 먼저 분리하고 명령은 얇게 유지 |
| `tick_driver.py` 240행 | 틱 스케줄과 훅 소유권. 게임 import 없음 | 현재 경계 양호. lifecycle 예외·재설치 계약 테스트 유지 |
| 게임 `bridge_client.py` 431행 | 전송 상태머신·버퍼·인증·재시도. 게임 import 없음 | 상태머신 응집도는 적절. 단순히 길다는 이유로 조각내지 않음 |
| 외부 `event_socket.py` 585행 | 토큰/endpoint 파일, 프레임, 인증, 이벤트 스키마, 서버 lifecycle, mock 클라이언트 | 설정 저장·프레임/인증·서버·테스트 클라이언트를 작은 경계로 분리할 후보 |
| `cli.py` 191행 | `main()` 135행에 인자 해석·파일 서비스·소켓 서비스·대화 처리·턴 한도 | 하위 command handler와 service loop 분리. CLI는 조립/표시만 담당 |
| `engine.py` 76행 | 한 요청 처리·검증·격리·공급자 호출 | 규모는 작음. 실패 정책과 저장 검증의 계약을 먼저 확정해야 함 |
| `save_lineage.py` 340행 + `save_slots.py` 113행 | 타입·순수 판별 함수·단위 테스트 | 모듈화 양호. 실제 게임 저장 hook/대화 engine에 아직 연결되지 않음 |
| `providers.py` 191행 | 공급자 interface·mock·OpenAI·응답 스키마 | 지금 당장 대형 plugin framework 불필요. 두 번째 실제 공급자를 붙일 때 분리 |

게임 모듈 분리 시 `build_game_mod.py`의 root-level `.pyc` 목록도 함께 바뀌어야 한다. 소스 테스트만 통과하고 배포 archive에 새 모듈을 빠뜨리는 회귀를 별도로 검사한다.

## 2. 이번 검토에서 직접 확인한 남은 결함

1. **다단어 치트 호출**: 로컬 `plumbmate_chat(message, _connection)`에 세 단어와 `_connection=None`을 bind하면 `TypeError: multiple values for argument '_connection'`가 재현된다. 페이블은 `*message_parts, _connection=None`로 수정했다. 그 회귀 테스트는 가짜 게임 모듈에서 “active Sim not found”까지 가는지 검사할 뿐, 활성 심→요청 파일→응답 표시를 증명하지 않는다. 무따옴표 여러 단어, 따옴표 문장, 한글·이모지를 실제 콘솔에서 각각 확인해야 한다. “모든 다단어 입력 100% 실패”라는 보고는 따옴표/엔진 파서 확인 없이 확대 인용하지 않는다.
2. **유니코드 경로 인덱스**: `/Users/İ/Mods/PlumbMate.ts4script/...`에서 원본 suffix 인덱스는 23, 전체 lower 결과는 24다. 로컬 `_mod_directory`의 슬라이싱은 잘못된다. 페이블의 원본 문자열 기준 검색을 채택할 후보다. 특정 OS 로케일이 아니라 Unicode 대소문자 변환 길이 문제다.
3. **비ASCII 숫자 호스트**: 로컬 `_is_loopback('１２７.０.０.１')`가 True다. ASCII 리터럴만 허용한다는 계약과 다르며 DNS 없는 연결이라는 가정이 깨진다. 페이블의 ASCII 숫자 검사와 관련 회귀 테스트를 통합할 후보다. 감사에서 외부 DNS 호출 자체는 실행하지 않았다.
4. **공개 스키마와 실행 검증의 불일치**: 요청 스키마는 ID 8~80자, actor 이름 120자, session 80자이나 로컬 검증은 ID hex32, 이름 128자, session 160자다. 스키마상 금지된 임의 최상위 필드도 `clamp_request`에 남는다. 합성 `undocumented_field=SYNTHETIC_MARKER`가 `RecordingProvider` 입력까지 전달됨을 확인했다. 외부 API 호출은 하지 않았다.
5. **내 추가 변경에도 응답 스키마 누락**: 로컬 engine이 붙인 `memory_policy`가 공개 response schema에 없다. `additionalProperties:false` 계약에 맞지 않는다. 검증 뒤 envelope를 바꾸는 방식부터 고쳐야 한다. 현재 단위 테스트는 공개 JSON Schema를 실행하지 않으므로 195개가 통과해도 이 문제가 남는다.

위 4~5번은 “정리용 리팩터링”보다 먼저 해결할 계약 결함이다. 일반 예외를 무조건 잡는 것만으로 스키마 검증을 대체하면 안 된다.

## 3. 페이블 변경과의 통합 계약

| 주제 | 루멘 로컬 | 페이블 PR | 통합 제안 |
|---|---|---|---|
| endpoint | 시작/명시적 재시작에서만 읽는 지속 설정. 기본 47651, 같은 포트 재연결 | 파일을 주기적으로 읽고 mtime 생존 신호·커널 포트 변경 추적 | 게임 틱 파일 I/O 금지 유지. 무명시 포트 변경/토큰 교체는 별도 제어 경로 없이는 자동화됐다고 주장하지 않음 |
| 훅/stop/reload | 실제 wrapper 객체와 class registry, suspend/binder 해제 | wrapper 상태/리로드 driver 재바인딩, stop 시 binder 해제 | 둘 중 하나의 소유권 구현만 남기고 양쪽 회귀 테스트를 통과시킴. stop은 새 소켓 생성 실패와 무관하게 작동해야 함 |
| 수신 프레임 | 버퍼 우선 + 완성 프레임 크기 상한 + 중복 ACK 통계 방어 | 버퍼 우선·keepalive·미전송 outbox 이관·중복 ACK 방어 | 버퍼 예산 유지, keepalive·미전송 이관 추가 검토. 전송 결과 불확실한 이벤트를 재전송하지 않음 |
| 외부 서버 lifecycle | 초기 accept/stop 경로에 감사 결함 남음 | stop 순서, 일시 accept 오류, handshake 전체 deadline, worker start 실패 처리 | 페이블 변경과 결정론적 테스트 채택 우선. deadline은 per-recv timeout과 구분 |
| 공급자 실패 | 불확실한 요청은 격리, 자동 재시도 안 함 | 최대 5회 재시도 후 격리 | 비용 정책 결정 필요. 네트워크 연결 재시도와 유료 모델 요청 재시도는 별개. 과금 여부 불명확한 모델 요청은 자동 재시도하지 않는 보수적 기본값 권고 |
| 기억 | 검증된 save scope가 없어 세션 기억 복원·모델 patch 승격을 차단 | 손상된 session 파일을 무시하고 다시 시작, 모델 patch 기반 memory_facts 유지 | 파일 손상 복구만으로 출처/세이브 격리 문제가 해결되지는 않음. 모델 추론≠관찰 사실 원칙 유지 |
| 자동 테스트 | 로컬 195개, 실제 게임 Python 3.7 빌드 | 다른 195개, macOS·Ubuntu CI와 3.7 구문 가드 | 테스트를 합집합으로 검토하고 계약이 바뀐 테스트는 이유와 함께 갱신. 단순 합산 수치 금지 |

PR의 서버 변경을 읽고 근거를 확인했지만, 전달된 “반박자 3명 전원 재현”의 개별 감사 산출물 전부를 읽은 것은 아니다. 코드·회귀 테스트·CI 근거와 보고자의 설명을 구분한다.

## 4. 초기 기획과 실제 연결 상태

| 사용자 경험 | 현재 코드/증거 | 아직 필요한 것 |
|---|---|---|
| 심 상태를 작은 텍스트로 받아 대화 | 수동 파일 요청, mock/선택형 공급자, 응답 표시 | 여러 단어 입력을 포함한 실제 콘솔 왕복, 선택된 AI 심과 플레이어 심 구분 |
| 게임 이벤트를 이미지 없이 관찰 | 소켓 heartbeat 및 allow-list 운반 가능 | 실제 이벤트 listener, Actor/Target·출처, Scene Atomizer, 관찰 범위 |
| 기억·취향을 가진 동료 | 세이브 계보 순수 함수와 문서 있음 | 저장 hook/검증 receipt, 외부 기억 DB·마이그레이션·조회 연결. 현재 기억 재사용 차단은 임시 안전조치이지 완성 기능이 아님 |
| 스스로 행동하는 두 번째 플레이어 | 실제 일반 행동 실행 비활성, ownership probe는 별도 진단 | 심 지정, 행동 catalogue, Dispatcher/Arbiter, player 우선권·생존·zone/save 가드, 완료 관찰 |
| L0/L1/L2/L3와 IC | 목표 문서에 있음 | 실제 Router/IC scheduler/ToneShadow와 상태머신은 미구현 |
| 비용을 조절하는 API 사용 | 입력 추정치·출력 상한, 로컬 run의 시도 횟수 상한 | 공급자 usage 실제 기록, 통화 비용/일일 한도, 동의 UI. 횟수 상한은 돈 한도가 아님 |

따라서 “클로드와 시험했을 때 돌아갔다”는 관측을 부정하지 않는다. 연결/일부 대화가 동작하는 것과, 기억·자율행동까지 초기 기획대로 연결된 것은 서로 다른 검증 단계다.

## 5. 유지보수 루틴 제안

- **매 변경**: 문제 재현→가장 작은 수정→회귀 테스트. 기능 추가와 대규모 이동/이름 변경은 같은 commit에 섞지 않는다.
- **두 작업 통합 전**: 공개 스키마, 실패/비용 정책, save scope, 스레드/파일 I/O 경계를 diff로 확인한다. 계약이 다른 두 구현을 함께 남기지 않는다.
- **공통 CI**: macOS+Ubuntu, Python 3.7 구문 가드, 실제 JSON Schema 계약 테스트, 비ASCII/잘못된 타입/부분 프레임/중복/시간초과/정지 후 호출 등 적대적 픽스처. 실제 게임 빌드는 별도 단계다.
- **실행 경로 하나가 연결될 때**: 명령→요청→공급자→정확한 응답→게임 표시까지 positive E2E. 가짜 게임 모듈 테스트는 엔진 검증으로 표시하지 않는다.
- **기능 묶음마다 작은 구조 점검**: 한 파일이 UI·정책·저장을 동시에 바꾸게 되거나 같은 규칙을 여러 파일에서 수정할 때 분리한다. “주기적 최적화”를 무조건 코드 재작성으로 해석하지 않는다.
- **성능은 측정 후**: 실제 틱 p95/p99, 처리 프레임·바이트, 큐 길이, 연결 재시도, API 시도/토큰을 측정한다. 테스트 개수·짧은 코드·단축어 수를 성능 지표로 대체하지 않는다.
- **새 추상화는 실제 사용처가 생길 때**: 모든 RFC 이름을 빈 class로 미리 만들거나 단일 메서드 파일을 대량 생성하지 않는다. 초기 분리 대상은 commands/runtime, socket 설정/framing/server, CLI handler다.

## 권장 다음 순서

1. 루멘 스냅샷을 별도 브랜치로 인계. main/PR #1은 그대로 유지.
2. 두 계약을 합의하고 페이블 고유 수정과 루멘 고유 수정·테스트를 작은 통합 commit으로 합침.
3. 요청/응답 스키마를 단일 기준으로 맞추고 게임 build/import 검증.
4. 수정본으로 저장 없는 인게임 다단어 채팅→응답 표시, 연결/정지/재연결 확인.
5. 그 기준선을 만든 다음 책임 분리 리팩터링. 이후 자동 관찰→단일 안전 행동→검증된 기억 순으로 구현.

현재 브랜치는 통합용 작업 스냅샷이며 배포 승인·인게임 검증 완료·PR 병합 완료를 뜻하지 않는다.
