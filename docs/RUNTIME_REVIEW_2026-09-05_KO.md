# 연구 보고서 검토와 미해결 런타임 시험

기준일: 2026-09-05. 대상 게임: 로컬 설치본 1.127.41.1230.

에이든의 기술 검토 보고서에서 우선 채택할 것은 외부 앱 분리, 실행 권한 단계화, 큐 점유·로드 순서 시험이다. 보고서의 일부 결론은 현재 PlumbMate 구현을 보지 않고 추정했거나 인용한 자료보다 강하게 단정했다. 아래 판단은 코드·제작자 자료·로컬 정적 분석에 근거하며, 실제 게임 시험을 통과했다는 뜻은 아니다.

## 1. 보고서에서 얻은 것과 수정할 것

| 보고서 주장 | 검토 결과와 설계 결정 |
|---|---|
| 외부 앱 + 게임 브리지 선례가 있다 | 채택. [Sentient Sims App 제작자 문서](https://github.com/guspuffygit/sentient-sims-app)는 외부 API 통신 및 모드 상태·저장을 동반 앱이 맡는다고 설명한다. 정확한 저장 동기화·스레딩의 안정성까지 README로 확인되지는 않는다. |
| 기존 AI 모드는 모두 대화만 하며 자율행동을 하지 않는다 | 수정. [dnavaria/sims4ai 실행 코드](https://github.com/dnavaria/sims4ai/blob/master/sims4_ai_mod/ai_sim_mod/tool_executor.py)에 이동·주입·취소 시도가 있다. 실패 시 `proposed_only`로 낮추는 프로토타입이므로 자율행동 시도의 존재와 실게임 안정성은 구분한다. 경쟁 사례를 근거로 우리 핵심 기능을 포기하거나 이미 검증됐다고 주장하지 않는다. |
| 폴링은 현실 시간 3초 미만 금지 | 기각. [TURBODRIVER 설명](https://turbodriver.io/simulation)은 게임 시간 3분 이하의 반복 알람을 Active 작업으로 집계한다는 진단 기준이다. 현실 시간 3초 하한이나 보편적 금지 규칙이 아니다. 게임 틱 처리시간·알람 수·대기량을 측정한다. |
| SQLite를 포기하고 게임 세이브에 기억을 넣어야 한다 | 이 결론은 불필요하다. 외부 SQLite를 유지하면서 분기와 저장 커밋에 기억을 귀속한다. 게임 내부 sqlite3의 유무는 외부 DB 채택 여부를 결정하지 않는다. |
| 슬롯 ID + 게임 시각이면 롤백 정합성을 확보한다 | 불충분. 일시정지 중 연속 저장과 같은 시각의 분기는 같은 키를 가질 수 있다. `save_scope + save_commit_id + watermark`와 실제 로드 세이브 매칭을 검증한다. |
| 현재 PlumbMate가 세이브와 무관하게 DB를 append-only로 쌓는다 | 현재 구현에 SQLite 기억 저장은 없다. 마스터에는 저장 경계가 설계돼 있으나 구현 전이다. 설계 누락과 구현 미완료를 구분한다. |
| 소스 `.py`를 넣으면 미래 Python 변경에도 자동으로 살아남는다 | 근거 부족이며 보고서의 `.pyc` 전용 주장과도 충돌한다. 인용된 [SimAI 빌드 코드](https://github.com/dnavaria/sims4ai/blob/master/sims4_ai_mod/build.py)도 3.7 바이트코드 생성 방식을 사용한다. 특정 패치부터 로더가 바뀌었다는 주장 자체는 별도 검증 대상이다. 우리 배포 기준은 설치본 바이트코드·로더 시험이다. |
| WW와의 충돌을 100% 억제해야만 자율성 v1 가능 | 실용적인 출시 기준으로 바꾼다. 검증된 버전 조합, 제한된 행동 목록, 점유 중 양보, 상태 불명확 시 주입 중단, 플레이어 행동 오인 취소 0건을 측정한다. 임의의 모든 모드 조합에 대한 보증은 하지 않는다. |

보고서의 EA 정책·특정 모드 최신판 번호·Memory Boost 인과·패치 날짜 전체를 이번 검토에서 재검증한 것은 아니다. 이 항목들은 배포 시 공식 자료로 확인한다. 연구 원문이나 제3자 코드를 프로젝트에 복사하지 않았다.

## 2. 실제 구현 상태

현재 `game_mod/src/plumbmate_mod/commands.py`는 사용자가 명령을 실행할 때 파일 기반 요청/응답과 작은 스냅샷을 처리한다. 실제 행동 주입, 자동 이벤트 관찰, 저장 연동, 기억 DB와 로컬 소켓 인증은 구현되지 않았다.

외부 API 대기는 동반 프로세스에서 하지만 게임 명령의 파일 읽기·쓰기는 동기다. 수동 프로토타입 왕복을 운영용 비차단 수집기가 완성된 것으로 표현하지 않는다. 이벤트 기반 버전에서는 콜백에서 메모리 큐까지만 쓰고 작업자가 I/O를 처리한다.

PM-Wire는 메시지 의미·버전·식별자의 계약이며 전송 방식과 별개다. 향후 루프백 소켓을 선택하면 루프백에만 bind하고 세션 인증·크기 제한·오래된 메시지 거절을 포함한다. 토큰만으로 같은 사용자 권한의 악성 프로세스까지 막는다고 주장하지 않는다.

## 3. 이벤트 채널 결과

| 관찰 | 설치본에서 확인한 경로 | 등록 방식 |
|---|---|---|
| 상호작용 완료 | `InteractionComplete → EventManagerService` | 공통 이벤트 handler |
| buff 시작/종료 | `BuffBeganEvent / BuffEndedEvent → EventManagerService` | 같은 관리자에 필요한 event types 등록 |
| 대표 기분 변경 | `MoodChange → EventManagerService` | 같은 관리자 |
| 욕구 수치 | statistic tracker watcher 및 continuous statistic 임계치 콜백 | 관리 심의 tracker/기존 statistic별 등록 |

결론은 “공통 이벤트 수신기 + 욕구 수신기를 한 정규화 단계로 합친다”다. 정적 경로는 확인됐고, live 수신 누락·빈도·등록 해제는 시험 전이다. 구체 심볼과 member 해시는 [빌드 증거표](runtime-evidence/TS4_1.127.41.1230_KO.md)에 기록했다.

이벤트 시험의 수용 조건:

- 양방향 상호작용에서 참여자별 완료 알림을 합쳐 사건 1개로 기록한다. 주행위자와 다른 참여자를 혼동하지 않는다.
- 취소·경로 실패·reset을 성공한 포옹/식사로 승격하지 않는다.
- buff 발생·종료와 mood 변경의 순서가 달라도 최신 상태가 일치한다. 모든 buff가 mood 변경을 일으킨다고 가정하지 않는다.
- 욕구 직접 변화와 아무 행동 없는 자연 감소를 각각 시험한다. 일시정지·속도 1/3·로드 후 임계치가 동작하는지 확인한다.
- 가족 전환·로트 전환·재등록 반복 후 리스너 개수가 증가하지 않는다. load 시 기존 buff를 새 사건으로 기록하지 않는다.
- 콜백에서는 I/O·모델 호출을 하지 않는다. 실제 게임 틱 시간과 누락·넘침 수치를 기록한다.

## 4. `_plumbmate_decision_id` 시험 명세

상태: **NOT_TESTED — 실제 enqueue 실행기와 개발용 계측이 아직 없음.** 일반 객체에 `setattr`이 된다는 확인이나 가짜 큐 단위시험으로 이 상태를 통과 처리하지 않는다.

각 단계의 계측 필드:

```text
build, session_uuid, scene_epoch, decision_id, actor_id,
runtime_identity, marker, parent_identity, phase,
ownership_state, cancellation_requested_by
```

`runtime_identity`는 세션·객체 수명 내 진단값이다. Python `id(obj)`나 게임 interaction ID 하나를 영속 소유권 키로 쓰지 않는다.

| 시험 | 마커 관찰 | 제품 합격 조건 |
|---|---|---|
| enqueue | 실제 생성 객체에 설정·즉시 재조회 | `PENDING`은 의도뿐. 정확한 객체와 주입 결과가 확인됐을 때 `BOUND` |
| start | 대기→실행에서 객체·마커 비교 | 검증된 객체 연결이 유지됨. 미확인 교체는 취소 권한 없음 |
| continuation | 부모·자식 객체와 각각의 마커 | 실제 부모→자식 관계가 관찰된 경우에만 소유권 계승 |
| cancel 대조군 | 플레이어/다른 모드가 동일 행동·대상을 실행 | PlumbMate의 취소 대상에 대조군이 포함되는 사례 0건 |
| Sim reset | 이전 객체·늦은 콜백·새 인스턴스 | 이전 연결 종료. 늦은 응답 무시. 목표만 재계획 |
| lot unload | 이동 전후 ID·zone·epoch | 새 로트의 같은 숫자 ID를 이전 실행으로 오인하지 않음 |
| save/load/rollback | 원장·마커와 저장 경계 | 과거 런타임 큐 재생 금지. 확인된 커밋의 목표만 복원 |

마커 유지성은 단계별 `SUPPORTED / UNSUPPORTED / NOT_TESTED`로 기록한다. 마커가 사라져도 검증된 원장으로 안전하게 처리할 수 있다면 제품 소유권 시험은 통과할 수 있다. 반대로 마커가 남아도 플레이어·타 모드 행동에 취소 권한을 잘못 부여하면 즉시 실패다. 테스트 도중 `ownership=unknown`으로 양보하는 것은 실패를 숨긴 성공이 아니라 명시적인 안전 결과이며 발생률을 별도 기록한다.

## 5. 이번 문서 반영

마스터의 이벤트 수신부, `PENDING→BOUND` 소유권, 저장 커밋 식별, 초기 행동 상한 및 WorldTrace 비동기 기록을 구체화했다. 이전의 “관찰 즉시 SQLite write-through” 문구는 게임 스레드 비차단 원칙과 충돌하여 고쳤다. 게임 플레이·Mods·Saves 설정 변경이나 동적 속성 설치 시험은 수행하지 않았다.
