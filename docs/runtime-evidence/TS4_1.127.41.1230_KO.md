## 자동저장 슬롯 — 정적 경로 확인

`services/persistence_service.pyc` 모듈 본문에서 `AUTO_SAVE_SLOT_ID = 4294967295` (`0xffffffff`)를 확인했다. member SHA-256: `96d4ffd7c4696232306d7aff7ae977c5d9eeaa5599425b71a4df984dcecc58d1`.

`PersistenceService.save_game_gen`은 성공 결과, `slot_id > 1`, `slot_id != AUTO_SAVE_SLOT_ID`일 때 manual-save-complete 콜백을 호출한다. 이 검사 자체도 `send_save_message` 분기 안에 있으므로 해당 manual 콜백 하나를 모든 저장의 완료 신호로 쓰면 안 된다.

현재 빌드의 `AutosaveService`는 실제 존재하며 실시간/게임시간/건축 종료 설정을 읽고 `REQUEST_AUTOSAVE` op를 클라이언트로 전달한다. 해당 슬롯을 현재 빌드의 engine autosave reserved slot으로 구분할 근거다. 그러나 일반 슬롯을 사용하는 타 모드 자동저장까지 manual이라고 분류할 근거는 아니며, 공유 예약 슬롯 ID는 세이브 계보 정체성도 아니다. 실제 자동저장은 테스트를 위해 실행하지 않았다.

## 2026-09-05 zone tick 주입 지점 정적 확인

게임의 `libpython370.dylib`로 `zone.pyc`를 marshal 로드하고 code object를 직접 읽었다. 게임 모듈을 import하거나 게임을 실행하지 않았다.

- `Zone.update`가 존재하며 `co_argcount=2`, `co_varnames[:2] == ('self', 'absolute_ticks')`다.
- 같은 클래스에 `_gather_tick_metrics(self, absolute_ticks)`, `tick_data(self)`, `start_gathering_tick_metrics`, `stop_gathering_tick_metrics`가 함께 있다. 이 이름들은 `update`가 프레임 단위 tick 경로라는 정황이지 호출 빈도의 증거는 아니다.
- `Zone`에는 `register_callback`/`unregister_callback`도 있으나 확인한 범위에서는 zone 수명주기 콜백이며 tick 콜백이 아니다. 그래서 등록 API 대신 `update` wrapper를 썼다.
- member SHA-256: `735c3463d9f8bcaf88f5d2f530c03556cf79a741a07bba72430ddb416ccf5658`
- 검사에 쓴 Python: `3.7.0` (게임 내장 런타임)

`plumbmate_tick_driver.install_tick_hook`은 원본을 먼저 호출한 뒤 `driver.on_tick(absolute_ticks)`을 부른다. 원본이 예외를 던지면 pump는 실행되지 않는다.

이것은 시그니처 존재에 대한 정적 증거일 뿐이다. 실제 호출 빈도, 한 tick의 예산, 다른 모드가 같은 메서드를 감쌌을 때의 순서, 게임 종료 시 wrapper 잔존 여부는 **NOT_TESTED**다.

## socket 사용 가능 여부 — 미검증 (소켓 브리지의 전제)

기존 격리 진단에서 `_socket.dylib`는 게임 Frameworks에 존재하지만 진단 실행 파일 위치에서 `@executable_path` 문제로 임포트에 실패했다. 따라서 **게임 프로세스 안에서 `import socket`이 성공하는지는 아직 확인되지 않았다.**

`base.zip`의 `lib/`에서 확인한 것은 다음과 같다.

| 모듈 | 확인 |
|---|---|
| `socket` | `lib/socket.pyc` 존재 |
| `hmac` | `lib/hmac.pyc` 존재 |
| `hashlib` | `lib/hashlib.pyc` 존재 |
| `json` | `lib/json/` 패키지 존재 |
| `uuid` | `lib/uuid.pyc` 존재 |

`select`가 없으므로 게임 측 클라이언트는 이를 import하지 않고 `getpeername`/`SO_ERROR`로 연결 완료를 판별한다. `errno`와 `time`은 CPython 코어 빌트인이다.

순수 Python 래퍼가 있다는 것이 확장 모듈 `_socket`이 게임 안에서 로드된다는 뜻은 아니다. `commands.py`는 이 때문에 `plumbmate_bridge_client` 임포트를 guard하고, 실패하면 소켓 브리지를 unavailable로 표시한 뒤 파일시스템 브리지로 계속 동작한다. 인게임 임포트 확인은 출시 전 재검증 항목이다.

## 2026-09-05 이벤트 채널 정적 확인

공통 관리자 등록은 `EventManagerService.register(handler, event_types)`이며 수신 규약은 `handler.handle_event(sim_info, event_type, resolver)`다. `_process_test_event` 바이트코드가 이 메서드를 직접 호출하는 것을 확인했다. 이름이 비공개인 emitter 메서드를 패치할 필요 없이 등록 경로를 우선 검증할 수 있다. 이는 EA가 안정성을 보장하는 공개 모딩 API라는 주장은 아니다.

욕구는 tracker에 별도로 등록한다. `create_and_add_listener`는 조건에 따라 statistic을 추가할 수 있으므로 읽기 전용 관찰기는 이미 존재하는 statistic만 선택하고 등록 부작용을 확인해야 한다. 일반 `notify_watchers`의 콜백 인자는 `(stat_type, old_value, new_value)`다. 초기 기준값과 임계치 동작은 게임 내에서 검증한다.

## 동적 마커와 격리 임포트의 한계

`Interaction.__init__`가 context를 `copy.copy`하고 `InteractionContext._clone`도 얕은 복사를 하는 경로를 확인했다. 이것은 context 복사의 증거이며, interaction 객체에 붙인 `_plumbmate_decision_id`가 자식 interaction에 전파되거나 사라진다는 증거가 아니다. 마커 유지성은 [실험 명세](../RUNTIME_REVIEW_2026-09-05_KO.md)의 단계별 `NOT_TESTED` 상태를 유지한다.

격리된 libpython 진단에서는 Python 3.7.0과 `.dylib` 확장 모듈 형식을 확인했다. `ssl.pyc`는 있으나 `_ssl`과 `sqlite3` 임포트는 실패했다. `_socket.dylib`는 게임 Frameworks에 실제로 있지만 진단 실행 파일 위치에서는 `@executable_path` 종속 경로가 달라 임포트에 실패했다. 따라서 이 실험으로 “게임에서도 socket이 없다”고 결론내리면 안 된다. 실제 게임 임포트 검사는 별도이며, 게임 안에서 HTTPS/SQLite를 사용하지 않는 제품 경계는 유지한다.
