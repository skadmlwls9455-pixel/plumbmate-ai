# 사용감과 장기 컨텍스트 검토

2026-09-06 검토 기록이다. 2026-09-07에 비용 원장·진단 CLI·ACK 기한·keepalive를 로컬 구현했고, 실제 사용 흐름에서 역할 지정과 UI의 공백을 확인했다. 최신 상태와 재개 순서는 [체크포인트](CHECKPOINT_2026-09-07_KO.md)를 우선한다. 아래 "현재/다음"은 검토 당시 기준이다.

## 결론

로그/소켓 왕복 성공은 플레이어 경험 완성의 증거가 아니다. 현재는 개발자용 콘솔 프로토타입이다. 장기 기억, 심 지정, 자동 행동, 자동 응답 표시를 완성됐다고 소개하면 안 된다.

## 지금 코드에 있는 것

| 관심사 | 실제 구현 | 한계 |
|---|---|---|
| 입력 안전성 | 하나의 JSON Schema에서 필드·타입·길이 검사; 추가 필드는 provider 전에 거절 | 형식 검증이 사실성/기억 출처 검증을 대신하지 않음 |

| 장기 기억 | 미검증 세이브의 기억 재사용 차단, 모델 memory_patch를 사실로 저장하지 않음 | 회상/취향/관계 성장 기능이 아직 연결되지 않았음 |

## 장기 플레이를 가볍게 만드는 원칙

저장 데이터량과 모델 입력량을 같은 것으로 취급하지 않는다. 미래의 DB에는 사건이 늘어나더라도 모델에는 현재 장면, 좁은 최근 버퍼, 관련 기억 일부만 보낸다. 전체 채팅 기록을 계속 붙이거나, 매 턴 전체 DB를 LLM에게 요약시키지 않는다.

우선순위는 ① 검증된 save/branch 범위 ② actor/target와 관찰 출처 ③ 현재 화제·상대·장소의 결정론적 후보 검색 ④ 후보 점수/중복 제거 ⑤ 고정 예산 packer다. 필요한 기억을 예산 밖으로 잘랐을 때는 "모른다/보류"를 허용해야 하며, 잘린 정보를 LLM이 채워 넣도록 유도하면 안 된다.

현재 12KB packer는 형식과 총량을 보장하는 기반이다. 항목의 의미적 중요도까지 이해하는 장기 기억 검색기가 아니다. 200턴 합성 mock 검사는 입력 히스토리의 자동 누적이 없음을 확인할 뿐, 몇 달 분량 DB 검색 속도나 RP 품질을 증명하지 않는다.

## 다음 사용자 경험 개선 순서

1. **설정과 상태 분리**: 실제 bridge 경로, 게임 모드 버전, companion 연결, provider 설정, 요청 처리 상태를 따로 보여주는 진단 화면. "소켓 연결됨"을 "AI 준비 완료"로 표시하지 않는다.
2. **한 번 입력 → 자동 응답 표시**: 치트창에서 chat/read를 번갈아 입력하는 흐름을 교체. 마지막 요청뿐 아니라 각 요청 ID를 매칭하고, 중복 표시·이전 로트 응답을 차단한다. 게임 틱의 파일 I/O를 다시 도입하지 말고 별도 bounded 응답 채널을 설계한다.
3. **누구와 대화하는지 명확히**: 선택 심과 AI 파트너 심을 분리해 표시. 현재는 active Sim 기반 스냅샷이지 완성된 다중 파트너 설정이 아니다.
4. **작은 수직 기능**: 관찰 사건 하나 → 출처 있는 기억 하나 → 적절한 회상 하나. 그다음 단일 허용 행동과 완료 관찰을 연결한다. RFC 이름의 빈 클래스부터 늘리지 않는다.
5. **실제 usage/비용 UI**: provider가 돌려준 input/output/cached usage를 기록하고 모델별 가격 정보와 구분한다. 추정치를 청구액처럼 표시하지 않는다. API 요청 직전 예산 예약과 일일 영속 한도를 두며, 프로세스 재시작/크래시 뒤 미확정 호출도 고려한다.

## 배포 전에 별도로 닫아야 하는 위험

- 동시에 두 companion engine이 같은 요청 디렉터리를 처리하는 경우와 API 호출 중 프로세스가 죽는 경우의 영속 claim/idempotency. 현재의 "자동 재시도 없음"은 살아 있는 단일 engine에서 처리된 실패에 대한 정책이다.
- 세이브 전환/가족 전환과 대기 응답의 격리, 검증된 save receipt 연결.
- 소켓 ACK deadline/keepalive/미전송 outbox 이관, endpoint 변경 UX.
- 보존 기간·로컬 기록 삭제/내보내기와 디스크 사용량 상한. 프롬프트가 제한되어도 디스크 archive는 계속 늘어난다.
- 정확한 모델별 출력 제한/실제 usage 처리와 prompt-cache key 정책. 캐싱 요청 필드가 있다는 이유만으로 절약률을 보장하지 않는다.
- macOS/Ubuntu 오프라인 검사와 실제 Sims 4 검사 분리. Windows 설치/방화벽/키 저장은 추가 실환경 검증 필요.
